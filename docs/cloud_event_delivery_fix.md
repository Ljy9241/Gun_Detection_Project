# 云端事件上传与 Flash 回收修复（2026-11-18）

## 原因

识别算法运行在设备上，云端根据上传记录的 `shotId` 建立事件。
原云端固件在采集期间仅上传 `recordKind=1` 的普通记录和有效 GPS 记录；
事件记录被排除，只有 `sealCollection()` 标记采集结束后才进入完整上传。
因此，网页看不到事件不能直接判定为设备漏识别。

实时普通/GPS 回执原来仅推进 `plainSeq`、`gpsSeq`，没有进入
`acknowledgeBatch()`，也就没有回收对应 Flash 文件。

## 修改后的完整流程

1. 保持设备端原有运动判定、阈值和计数规则，事件先写入 Flash。
2. 在采集期间优先发送已保存的射击事件，支持没有 GPS 定位的事件。
3. 与优先事件批次交替发送完整队列的最早记录，普通数据、GPS、旧格式记录和事件都可补传，不再等待采集结束。
4. HTTPS 返回后核对 `committed`、设备、存储代号、批次、数量及每条记录身份。
5. 优先事件回执不会越过尚未上传的普通记录。完整队列回执推进连续确认位置。
6. 完整队列批次核对成功后，先持久化整批确认位置，再删除其中全部记录已确认的分段文件，释放容量。
7. 文件删除失败时保留文件并定期重试。网络或确认位置持久化失败时，保持相同批次重试。

文件以 32 KiB 分段回收；有未确认记录的分段暂时保留。这里是缓存文件回收，不是整片 Flash 格式化，也不是安全擦除。
上传期间写入的新记录不会因旧批次回执被删除。

优先上传的事件之后可能随完整队列再次上传；服务端按记录身份去重，事件只计数一次。
旧固件已上传但尚未回收的记录也通过重传、去重和确认流程回收。
整批确认位置已持久化后重启，会从该位置继续；若云端已入库但本地确认位置尚未保存，则允许安全重传。

## 验证

- `archive_queue_test.cpp` 直接运行生产版上传调度和 Flash 队列代码，以内存文件系统/NVS 注入故障。
- 覆盖未结束采集的事件、没有 GPS 的事件、历史积压时事件优先、队列公平补传、上传中新增数据、跨分段回收、错误身份、丢失回执、NVS 写失败、读失败、重启重传、删除失败重试、损坏尾部保留。
- `cloud_backend/tests/test_receiver.py` 覆盖优先事件入库后完整队列重传、回执身份和去重计数。
- 原始 CSV 回放：横向 30 次识别 30 次；纵向 30 次，射击计数 0。

实机验收应依次确认串口 `SHOT #`、`Shot priority ... committed`、网页事件，以及
`Flash reclaimed` 和 `flash_pending` 的变化。重复上传不应增加射击次数；断网时缓存应保留。
当前验证不等同于新固件已烧录或用户本次动作已经在实机重现。

## 边界

上传依赖联网及有效系统时间。网络失败时不会承诺实时到达。
Flash 不可写或已满时，原有事件写入会报告失败；没有成功保存的历史事件不能通过补传恢复。
损坏的文件尾部不会被当作正常文件结束并自动删除，需单独诊断。

## 后续日志：已用空间暂时不下降

用户提供的日志显示 `flash_pending` 从 33142 降到 33137，同时仍在写入新数据。
`used=3411968/12582912` 约为 27.1% 占用，仍有约 8.75 MiB 可用，不能据此判定 Flash 未清理。
LittleFS 的块占用不等于文件有效字节总和，小文件可能内联到共享元数据块；删除文件不保证每次都减少分配块数。
剩余约 3.3 万条记录仍需逐批收到有效回执后回收。

进一步修复：

- 回收扫描最初增加了 `exists()` 检查，但实机验证发现当前 Arduino LittleFS 的 `exists()` 本身也会以只读方式打开文件，仍会打印 `does not exist`；下述 11 月 19 日修复替换了这一做法。
- 新建/复用分段后更新实际写入位置；重启时按最新记录序号恢复写入位置。旧代码按最大文件编号选位置，复用较小编号后可能连续创建小文件。
- 删除日志增加 `file_bytes`，表示删除文件的逻辑字节数，与 `used` 的文件系统分配块占用分开判断。
- 新增回归测试：填满两个分段、回收低编号分段后复用、单条和批量继续追加、重启后继续写入同一分段，以及回收时不打开不存在的文件。

上述修复不格式化 Flash，也不跳过未确认的历史记录。

## 2026-11-19：提速及周期扫描阻塞修复

已经实现：跨文件按序合并最多 64 条，HTTPS 连接复用，成功后连续发送，整批只持久化一次确认位置，清理日志按批汇总。少于 64 条也立即发送，不等待凑满；射击事件继续优先补传。云端接口原本支持 64 条，无需为这一批量调整修改服务端协议。

用户实机日志已确认：

- `fifo=47.18 records/s`：完整队列确认速度约 47 条/秒。
- `inserted=19.26 records/s`：该窗口中的云端新增速度；其余包含重复记录的安全确认。
- 后续批次 `new_connections=0`：复用连接，单次 HTTP 耗时约 136～484 ms。
- 文件系统占用从 2928640 降到 2891776 字节，减少 36864 字节。
- 仍有扫描 512 个文件名产生报错，以及 `late=4767 ms skipped=1` 的周期保存延迟。日志同时显示 ADC 溢出为 0；二者属于不同环节。

本次进一步修改：

1. 挂载时使用静默 `stat()` 建立文件存在索引，创建、删除时同步更新；周期清理及分配文件位置直接使用索引，不再调用 `LittleFS.exists()`。探测遇到 I/O 错误不会把未知文件当作空闲位置覆盖。
2. 挂载和追加时记录各分段最后一个事件的序号，事件优先扫描跳过不含待传事件的普通数据文件。
3. 增加测试，确认空闲周期清理没有文件打开或磁盘探测；事件扫描只打开相关分段；重启后索引正确；失败删除仍可重试。

测试与限制：本机队列测试通过，云端测试 40 项通过。128 个单条碎片记录只需 2 个批次及 2 次确认位置写入。故障测试覆盖确认位置写失败、整批确认后部分文件操作失败及重试、重启恢复和保留新增记录。
本次索引修复的实际延迟改善仍需烧录后验证；47.18 条/秒是用户所贴上一版固件的测量值，不能当作本次修复后的测量结果。

云端模式在无线开启期间关闭 Wi-Fi 省电等待以降低传输延迟，代价是联网时功耗增加；无线关闭和既有休眠逻辑仍由原有调度控制。
