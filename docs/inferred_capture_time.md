# 未校时记录的生成时间推算与上传

## 实现行为

新版云端固件在同一次上电首次观察到有效系统 UTC 时，保存 `bootId`、UTC 毫秒和对应的 `uptimeMs`。GPS、NTP、USB 校时均可提供系统时间。即使 Wi-Fi 关闭，也会尝试保存时间基准。

对该次上电中、时间基准之前的 `T+…` 记录：

```text
生成 UTC 毫秒 = 基准 UTC 毫秒 −（基准 uptimeMs − 记录 uptimeMs）
```

上传字段 `timestamp` 使用换算后的北京时间，精确到秒，并附带原始 `T+…` 和时间基准。云端校验计算结果后保存；网页显示“（推算）”，按生成时间混合排列设备数据。接收时间不参与记录排序。没有时间基准的记录置后，按设备、存储批次和生成序号排列。

## 重试、重启与旧数据

- 每个 boot 的首次时间基准固定保存，后续校时不会改变已使用的推算结果。
- 基准文件保存在设备 LittleFS 的 `clock-<bootId>.dat`；写入、关闭、重命名并回读校验成功后才允许使用。保存失败时当前设备暂缓上传，保留记录并重试。
- 原始 90 字节 Flash 记录不改写，上传批次快照在重试期间保持不变。
- 基准文件随记录文件系统保留，应用分区升级或重启后可以用于对应旧 boot 的补传。它们不随普通记录分段回收；不要手动删除仍可能需要的基准文件。
- 云端按原始采集内容计算记录及批次摘要，增加推算时间不会改变去重身份。旧 `T+…` 已入库记录若再次携带推算信息上传，会补齐时间和日期，包括对应事件，但不会新增重复记录或事件。
- 云端已经保存的日历时间保持不变，不被后续不同推算结果覆盖；时间展示补齐不改变原始摘要。
- 不跨设备、不跨 boot 推算。某次上电从未获得有效时间，或者升级前没有保存该 boot 的基准，不能仅凭下一次开机的时间补出它的日期。
- 本次未执行云端历史记录全库回填。已经从设备回收、不会再次上传的历史 `T+…` 记录，需另行基于云端同 boot 的已校时记录做受控回填。

## 上传协议

格式名为 `compact-v4-time`，每行 18 项：前 15 项沿用 `compact-v3-tilt`；最后三项为：

| 索引（从 0 开始） | 内容 |
|---|---|
| 15 | 原始 `T+HH:MM:SS` 字符串 |
| 16 | 时间基准的 UTC 毫秒，十进制字符串 |
| 17 | 同 boot 时间基准的 uptimeMs，十进制字符串 |

已校时的普通记录、没有可用基准的旧记录，这三项全部为 `null`。推算记录的索引 1 是推算后的北京时间。云端存储额外字段 `original_timestamp`、`timestamp_source="inferred"`、`time_anchor`；日期筛选和事件按日统计使用推算日期。

无需数据库结构迁移。服务继续接受旧协议；旧服务不接受 v4，所以必须先更新云端。

## 发布顺序

1. 运行后端测试，并用 `deploy/build_bundle.py` 打包新的接收程序。
2. 按 [完整部署指南](new_device_deployment.md) 备份、更新云端接收服务，并更新 `viewer.py`、重启网页服务。
3. 编译并按设备身份分别烧录 `esp32-s3-cloud`；保留原分区、NVS、LittleFS 和 storageEpoch。
4. 不要只更新网页：服务端 `protocol.py`、`service.py` 与设备固件都需要升级。
5. 保留原设备配置，不把一台设备编译出的带身份固件复制到其他设备。

## 验证

自动验证覆盖：推算公式、跨 boot 拒绝、未来 uptime 拒绝、基准持久化和重新加载、首次基准固定、损坏检测、写失败、v4 时间校验、旧协议重传兼容、补齐已入库事件日期、去重和单位隔离。

实机仍需验证：冷启动暂不校时并采集 → 同次上电通过 NTP/GPS/USB 校时 → 上传显示正确推算时间 → 断网重传 → 保留缓存重启补传。推算精度受系统时间基准、设备时钟漂移和秒级显示影响，不等同于高精度授时。
